# Internationalization (i18n) & Localization

WelloWork is localized with [`next-intl`](https://next-intl.dev) v4 on the Next.js 16
App Router. **The URL is the single source of truth for locale.** English is the
default and lives on clean, unprefixed URLs (`/`, `/about`); every other enabled
locale is served under a subdirectory (`/de`, `/de/about`, …).

> **Note on `SEO_GUIDELINES.md`.** That file is referenced by the original brief but
> is **not present in this repo**. This implementation follows well-established
> international-SEO best practice and maps each decision to the *intent* of the
> referenced sections (see [SEO mapping](#seo-guideline-mapping)). If the guideline
> doc is added later, re-check this table against it.

## File map

| File | Responsibility |
| --- | --- |
| `i18n/locales.ts` | **The config source of truth.** All known locales + per-locale metadata (endonym, og:locale, hreflang, tier) and the single `PUBLISHED_LOCALES` switch (→ the derived `ENABLED_LOCALES`, which strips `en-XA` in production). |
| `i18n/routing.ts` | `defineRouting` — `locales` (from `ENABLED_LOCALES`), `defaultLocale`, `localePrefix: 'as-needed'`, `localeDetection: false`. |
| `i18n/request.ts` | Per-request config: loads only the active locale's messages; default-locale fallback for missing keys. |
| `i18n/navigation.ts` | Locale-aware `Link` / `useRouter` / `usePathname` / `redirect` wrappers. |
| `i18n/detection.ts` | The single deterministic resolver (`Accept-Language` → `COUNTRY_TO_LOCALE` → default) + the country map. |
| `proxy.ts` | **Next 16 middleware** (renamed from `middleware.ts`). Bot-safe, root-only seeding redirect + `next-intl` routing. |
| `app/[locale]/layout.tsx` | The root layout: `<html lang>`, fonts, `setRequestLocale`, `NextIntlClientProvider`, locale-aware default metadata. |
| `app/lib/site.ts` | Locale-aware SEO: `buildMetadata`, `localizedUrl`, `languageAlternates`, `breadcrumbList`, `organizationSchema`, `inLanguage`. |
| `app/sitemap.ts` | One entry per enabled locale per path + hreflang alternates. |
| `app/components/LocaleSwitcher.tsx` | Accessible toolbar switcher (endonyms, route-preserving, sticky cookie). |
| `app/components/LocaleSuggestionBanner.tsx` | Dismissible "view in <language>?" prompt (SEO-safe alternative to forced redirects). |
| `messages/en.json` | **Fully written** default catalog (source of truth for keys + types). |
| `messages/{de,fr,es,it}.json` | Scaffolded **drafts** — English-seeded, flagged, and **disabled** until reviewed. |
| `messages/en-XA.json` | Pseudo-locale for layout/overflow testing (force-disabled in production builds). |
| `global.d.ts` | Type-safe `Locale` + `Messages` (typo'd keys fail the build). |

## How locale is chosen

1. **The URL wins, always.** A request to `/de/...` renders German regardless of
   cookies or IP. `localeDetection` is disabled in `routing.ts` so there is exactly
   **one** redirect authority: `proxy.ts`.
2. **Seeding the first visit** (in `proxy.ts`) happens **only** when *all* of:
   - the path is the x-default root `/`, **and**
   - the visitor is **not a bot** (`isbot`), **and**
   - there is **no `NEXT_LOCALE` cookie**.

   Then the resolver runs in this order — **cookie → `Accept-Language` → IP country
   (`@vercel/functions` `geolocation()`) → default** — and, if it yields a non-default
   *enabled* locale, issues a **`307`** to `/<locale>` and sets `NEXT_LOCALE`
   (`Cache-Control: no-store`, because it is personalized).
3. **Everything else is never auto-redirected** — bots, deep URLs (`/about`,
   `/insights/...`), and anyone with a cookie. This keeps every locale URL directly
   crawlable and indexable (Googlebot crawls from US IPs).

The switcher and the suggestion banner both set `NEXT_LOCALE`, so a chosen language
is sticky for a year.

## Add / publish a locale

1. **Translate** `messages/<code>.json` (it already exists as an English-seeded draft
   for the Tier-1 set; for a new code, copy `messages/en.json` and translate the
   values). Never translate the brand tokens `WelloWork`, `WelloRise`, `WelloWize`.
2. **Enable it** — add the code to **one array**:
   ```ts
   // i18n/locales.ts
   const PUBLISHED_LOCALES: AppLocale[] = ['en', 'de']; // ← add 'de'
   ```
   That single edit flows (via the derived `ENABLED_LOCALES`) into routing, the
   switcher, hreflang alternates, the sitemap, and `generateStaticParams`. Disabled
   locales appear in **none** of them. (`en-XA` is special — it is force-stripped from
   `ENABLED_LOCALES` in production regardless of `PUBLISHED_LOCALES`, so the test locale
   can never ship.)
3. (Optional) extend `COUNTRY_TO_LOCALE` in `i18n/detection.ts` if you want IP-based
   seeding for that language's countries.

A locale not yet in `LOCALES`? Add its metadata entry (endonym, `ogLocale`,
`hreflang`) to `ALL_LOCALE_CODES` + `LOCALES` first. Region variants (`pt-PT`,
`en-GB`) can be added the same way without refactoring.

## Before enabling a locale — checklist

Enabling a locale is **content-only**; no code edits are required.

1. **Translate `messages/<code>.json`** — every value, including:
   - the per-route **`metadata`** namespace (page `<title>` + meta description — these
     drive SEO and are now catalog-driven, not hardcoded),
   - the **`forms.error.*`** keys (form-validation messages — the API returns
     locale-agnostic error *codes* that the client maps to these keys, so form errors
     localize too), and
   - the `localeSwitcher` UI strings.
   Keep the brand tokens `WelloWork` / `WelloRise` / `WelloWize` **verbatim**.
2. **Clear the draft flag** — delete the `_draft` object from that locale's file once a
   human has reviewed the translation. (Unreviewed/​machine drafts keep the flag.)
3. **Flip it on** — add the code to `PUBLISHED_LOCALES` in `i18n/locales.ts`. That single
   line wires routing, the switcher, hreflang, the sitemap and `generateStaticParams`.
4. **(Optional)** extend `COUNTRY_TO_LOCALE` in `i18n/detection.ts` for IP seeding.
5. **Verify** — `npm run build && npm test`, then check `/<code>` renders, the switcher
   lists it, and its pages emit a self-canonical + hreflang. The detection resolver
   **clamps to `ENABLED_LOCALES`**, so a disabled locale can never be a 307 target — but
   re-running `npm test` after the flip confirms the new locale resolves as expected.

## Add / translate message keys

- `messages/en.json` is the **source of truth** for both copy and types. Keys are
  grouped by **namespace** (`nav`, `home`, `footer`, `forms`, `platformGrowth`, …).
- Add a key to `en.json`, then add the same key to every enabled locale file. Missing
  keys in a non-default locale **fall back to the English string** at runtime
  (see `i18n/request.ts` `getMessageFallback`); in `development` the missing key is
  logged to the console.
- Read keys in components:
  ```tsx
  // sync component (server or 'use client')
  import {useTranslations} from 'next-intl';
  const t = useTranslations('nav');
  t('items.platform');

  // async server component / page
  import {getTranslations} from 'next-intl/server';
  const t = await getTranslations('home');
  ```
- Lists are stored as JSON arrays; read with `t.raw('some.list') as string[]`.
- Dates / numbers / currencies: use next-intl's formatter (`useFormatter` /
  `getFormatter`) — never hard-code a locale-specific format.

## Translation workflow (honesty rules)

- **No fabricated translations.** Only English is fully written and enabled at launch.
  `de/fr/es/it` ship as **disabled drafts** seeded with English and a `_draft` flag.
  They are **not routed, switchable, in hreflang, or in the sitemap** until a human
  reviews them and the code is added to `PUBLISHED_LOCALES`.
- The `_draft.status` field in each draft file marks it `NOT human-reviewed`.
- Machine-translated drafts, if used, must keep the `_draft` flag until reviewed —
  never present an unreviewed translation as production-ready.

## Testing

- **Unit tests** — `npm test` runs the resolver tests (`i18n/detection.test.ts`, via
  `node --test` + `tsx`). They assert the core SEO guarantees: an enabled locale resolves,
  a country/`Accept-Language` mapped to a **disabled** locale clamps to the default
  (never a 307 to an unrouted URL), and the bot/cookie/deep-URL paths never redirect.
- **Pseudo-locale** (`en-XA`): accented + padded English that preserves brand tokens
  and ICU placeholders — surfaces truncation/overflow and any string still hardcoded
  (un-accented text = not externalized). To test: temporarily add `'en-XA'` to
  `PUBLISHED_LOCALES`, run `npm run dev`, open `/en-XA`. **Revert before committing.**
  It only works in **dev** — `en-XA` is force-stripped from `ENABLED_LOCALES` in
  production (`NODE_ENV === 'production'`), so a left-in toggle 404s and is absent from
  the sitemap in a production build (verified).
- **Bot safety**: `curl -A 'Googlebot' http://localhost:3000/` must return the page
  directly (no 307). A normal browser at `/` with a non-English `Accept-Language`
  and no cookie gets a 307 to its locale (only once a 2nd locale is enabled, and
  only on Vercel for the IP part).
- **hreflang / canonical**: view source of any page — every enabled locale + a
  `x-default` `<link rel="alternate" hreflang>` and a self-referencing
  `<link rel="canonical">` must be present.

> **Lint baseline.** `npm run lint` reports two `react-hooks/set-state-in-effect`
> errors in `app/components/CalcomEmbed.tsx` and `app/components/LegalNav.tsx`. These are
> **pre-existing** (present before the i18n work) and unrelated to localization — tracked
> separately, not introduced here.

## Accessibility, performance & privacy

- The switcher is keyboard-operable (Enter/Space to open, Escape to close), has a
  visible focus ring (global `:focus-visible`), `aria-haspopup`/`aria-expanded`/
  `aria-current`, and each option carries its own `lang`/`hrefLang` so assistive tech
  pronounces endonyms correctly (WCAG 2.1 AA).
- Only the **active** locale's messages are imported per request (`i18n/request.ts`),
  so non-active catalogs never reach the client bundle (protects LCP / bundle size).
- The `NEXT_LOCALE` cookie is a **functional/necessary** cookie (language preference),
  generally exempt from consent under GDPR/ePrivacy. **Do not** gate language behind a
  consent banner. Document it in the privacy policy.
- All currently enabled European languages are LTR; `dir` is intentionally **not**
  hard-coded, so a future RTL locale can set `<html dir>` without a refactor.

## SEO guideline mapping

Maps each piece to the intent of the `SEO_GUIDELINES.md` sections named in the brief.

| Section (intent) | How it is satisfied |
| --- | --- |
| **§2.1 consistent brand entity** | `WelloWork` / `WelloRise` / `WelloWize` are never translated (enforced in `locales.ts`, scaffold generator, and `en.json` values). `organizationSchema` uses one stable `@id` (`${SITE_URL}#org`), identical across locales. |
| **§6.3 crawlability (robots / sitemap / canonical)** | Every locale URL is directly crawlable; `proxy.ts` never redirects bots. `app/robots.ts` keeps all locale paths allowed. `app/sitemap.ts` emits every enabled-locale URL with hreflang alternates. Self-referencing canonical per locale via `buildMetadata`. |
| **§6.1 Core Web Vitals** | Per-request single-locale message loading; static rendering via `setRequestLocale` + `generateStaticParams`; no layout-shifting client redirects on deep URLs. |
| **§7 schema** | `inLanguage` added to BreadcrumbList / Organization / Service / Article / CollectionPage / FAQPage nodes; JSON-LD URLs use `localizedUrl` so they match the page canonical. |
| **§9 international/global SEO** | Subdirectory routing (`/de/...`) with `localePrefix: 'as-needed'`; full `hreflang` + `x-default` coverage for enabled locales; endonyms in the switcher; locale-aware formatting. |
| **§9.1 locale-aware formatting** | next-intl formatter for dates/numbers/currencies (no hard-coded formats). |
| **§9.2 subdirectory recommended** | English on the apex/clean URLs; other locales under subdirectories. |
| **§14 never cloaking, never bad translations** | URL is the single source of truth; identical content served to bots and users; unreviewed locales stay disabled (`_draft` flag) and out of hreflang/sitemap until human-reviewed. |
